# SERVE on Render

How to run SERVE on [Render](https://render.com) with the repository's
[render.yaml](../render.yaml) Blueprint: **one Docker web service** that
serves all three web apps, the API and Socket.IO on Render's generated
`onrender.com` address, plus **a PostgreSQL database** that only services
inside Render can reach. No custom domain is needed.

| URL | What |
|---|---|
| `https://<RENDER_DOMAIN>/` | Student app (Flutter web build) |
| `https://<RENDER_DOMAIN>/staff/` | Staff dashboard |
| `https://<RENDER_DOMAIN>/admin/` | Admin portal |
| `https://<RENDER_DOMAIN>/api/…` | REST API (`/api/health`, `/api/health/db`) |
| `https://<RENDER_DOMAIN>/socket.io/` | Socket.IO realtime (WebSocket over TLS) |

`<RENDER_DOMAIN>` is the address Render assigns, e.g. `serve-xxxx.onrender.com`.
Render terminates HTTPS and forwards every request, including WebSocket
upgrades, to the container. No Caddy or nginx is involved.

## Free plans: for trying the deployment only

The Blueprint starts on Render's **free** plans so the production setup can be
tested at no cost. They are **not suitable for the university rollout**:

- A free web service **spins down after a period without traffic** (about 15
  minutes). The next request waits while it starts again (up to about a
  minute), and open Socket.IO connections drop until clients reconnect.
- Free instances have limited CPU and memory and a monthly usage allowance.
- A free Render Postgres database has limited storage, **no backups**, and
  **expires a limited time after it is created** (Render currently documents
  30 days). Its data is then lost unless it was upgraded or exported first.

Check Render's current plan pages for exact limits. Before real students,
staff and admins use SERVE, change both `plan` values (in the dashboard or
`render.yaml`) to paid plans, or point `DATABASE_URL` at another managed
PostgreSQL 16. The application needs no change for either.

## What the Blueprint creates

- **`serve`**, a web service built from the [Dockerfile](../Dockerfile)
  (region `singapore`; change it in `render.yaml` before the first deploy if
  most users are elsewhere). The image builds the backend, the staff and admin
  apps and the student web app from source. On every start
  [`backend/scripts/start-production.sh`](../backend/scripts/start-production.sh)
  runs:
  1. `prisma migrate deploy`: applies pending migrations, never resets or
     drops data;
  2. the release tasks ([src/ops/release.ts](../backend/src/ops/release.ts)):
     on an empty database the catalogue seed (hostels, canteens, menus), and,
     if configured, linking the first admin;
  3. the server, on Render's `PORT`, all interfaces.

  If step 1 or 2 fails, the new deploy does not go live and the previous one
  keeps serving. Render checks `/api/health` before switching traffic.
- **`serve-db`**, PostgreSQL 16 in the same region, with **no external
  access** (`ipAllowList: []`). The web service connects over Render's private
  network; the connection string becomes `DATABASE_URL` automatically.

## Step 1: Firebase production project

Follow [deployment.md, step 5](deployment.md#5-firebase-production-project):
create the project, enable **Email/Password**, add a **Web** app, and
generate a **service-account key**. Keep these four values ready; you enter
them in Render, never in Git or chat:

| Render variable | Where it comes from |
|---|---|
| `FIREBASE_PROJECT_ID` | Project settings → General → Project ID |
| `FIREBASE_API_KEY` | Project settings → General → Your apps → Web app → `apiKey` (public) |
| `FIREBASE_CLIENT_EMAIL` | the service-account JSON → `client_email` |
| `FIREBASE_PRIVATE_KEY` | the service-account JSON → `private_key`: the whole value, from `-----BEGIN PRIVATE KEY-----` to `-----END PRIVATE KEY-----` |

Delete the downloaded JSON file once the values are in Render.

## Step 2: Create the Blueprint

1. Sign in at [dashboard.render.com](https://dashboard.render.com).
2. **New → Blueprint**.
3. **Connect GitHub** if asked, and give Render access to the
   `krutthiikaaa/Serve-final` repository.
4. Choose the repository and the branch to deploy
   (`claude/vibrant-bardeen-mfn5w4` until it is merged; then `main`).
5. Render reads `render.yaml` and lists `serve` and `serve-db`. Give the
   Blueprint a name (e.g. `serve`).
6. Fill in the four Firebase variables from step 1. `PAYMENT_SECRET` is
   generated by Render; the other values come from `render.yaml`.
7. **Apply**. Render creates the database, then builds and deploys the web
   service.

The first build takes a while (it downloads the Flutter SDK and builds three
apps). Follow it under **serve → Events / Logs**. A successful start logs, in
order: the migrations (`All migrations have been successfully applied` the
first time, `No pending migrations to apply` later), `Catalogue seeded (empty
database)` on the first start, `SERVE backend listening on port 10000`, and a
`DEMO_MODE` warning.

## Step 3: Check the deployment

The service page shows the public URL. Open, in a browser:

- `https://<RENDER_DOMAIN>/api/health` and `/api/health/db`: `"status":"ok"`
- `https://<RENDER_DOMAIN>/`, `/staff/` and `/admin/`: the three apps

Then, from a computer with the repository:

```bash
npm run smoke:deploy -- https://<RENDER_DOMAIN>
```

## Step 4: First admin

There is no public admin sign-up. Using the existing provisioning flow:

1. Firebase console → **Authentication → Users → Add user**: the admin's email
   and a strong password.
2. Render → **serve → Environment → Add environment variable**:
   `ADMIN_BOOTSTRAP_EMAIL` = that email, `ADMIN_BOOTSTRAP_NAME` = the admin's
   name. **Save, rebuild and deploy** (or Save and deploy).
3. The deploy log shows `First admin linked`. Sign in at `/admin/`.
4. Optional: remove the two variables again. The admin stays; the step is
   idempotent and never creates Firebase users or touches other accounts.

## Step 5: Staff, students and the acceptance test

- Staff create an account at `/staff/create-account` and request a canteen;
  the admin approves them in `/admin/`.
- Students register in the app (web at `/`, or the mobile app, step 6).
- With a student, an approved staff member and the admin, run the signed-in
  acceptance test ([deployment.md, step 18](deployment.md#18-production-testing)):

  ```bash
  FIREBASE_API_KEY=… ACCEPT_STUDENT_EMAIL=… ACCEPT_STUDENT_PASSWORD=… \
  ACCEPT_STAFF_EMAIL=… ACCEPT_STAFF_PASSWORD=… ACCEPT_ADMIN_EMAIL=… ACCEPT_ADMIN_PASSWORD=… \
  npm run acceptance:deploy -- https://<RENDER_DOMAIN>
  ```

  It places one simulated order and walks it to COLLECTED with live updates,
  briefly toggles one menu item, and checks the role refusals.

## Step 6: The student mobile app

```bash
cd apps/student
cp config/production.example.json config/production.json   # gitignored
```

Set `API_URL` to `https://<RENDER_DOMAIN>` (`https://<RENDER_DOMAIN>/api` is
accepted too; the app calls `/api/…` and `/socket.io` under it) and the two
public Firebase values. Then build or run it as in
[deployment.md, steps 15–17](deployment.md#15-mobile-api-configuration):

```bash
flutter run --release -d <device-id> --dart-define-from-file=config/production.json
flutter build apk --release --dart-define-from-file=config/production.json
```

If the Firebase web API key is restricted to the website, the mobile app
cannot sign in; see [deployment.md, step 5.4](deployment.md#5-firebase-production-project).

## Environment variables

Names are the ones the code reads ([backend/src/config/env.ts](../backend/src/config/env.ts));
the server refuses to start on an invalid value and names the variable
without printing it.

### Production (Render: serve → Environment)

| Variable | Value | Set by | Secret |
|---|---|---|---|
| `NODE_ENV` | `production` | render.yaml | no |
| `PORT` | `10000` | Render | no |
| `DATABASE_URL` | internal connection string of `serve-db` | render.yaml (`fromDatabase`) | **yes** |
| `CORS_ORIGINS` | unset: defaults to `RENDER_EXTERNAL_URL` (set by Render). Set it only to add other https origins | Render | no |
| `TRUST_PROXY` | `1` (Render's proxy) | render.yaml | no |
| `LOG_LEVEL` | `info` | render.yaml | no |
| `FIREBASE_PROJECT_ID` | step 1 | you | no |
| `FIREBASE_API_KEY` | step 1; used by the web build | you | no (public) |
| `FIREBASE_CLIENT_EMAIL` | step 1 | you | **yes** |
| `FIREBASE_PRIVATE_KEY` | step 1 | you | **yes** |
| `PAYMENT_MODE` | `mock` | render.yaml | no |
| `DEMO_MODE` | `true` (required with `mock` in production) | render.yaml | no |
| `PAYMENT_SECRET` | random | render.yaml (`generateValue`) | **yes** |
| `ADMIN_BOOTSTRAP_EMAIL`, `ADMIN_BOOTSTRAP_NAME` | optional, step 4 | you | no |
| `STUDENT_EMAIL_DOMAINS` | optional: only these email domains may register as students | you | no |
| `WEB_ROOT` | `/app/web` | the image | no |
| `FIREBASE_AUTH_EMULATOR_HOST` | **never set** (production refuses it) | — | — |

Production accepts no localhost values: localhost or http CORS origins, the
emulator, `demo-` Firebase projects and the local `serve_dev` / `serve_test`
databases are all refused at startup. The web apps and Socket.IO need no API
or socket URL: they use the origin that served them (`VITE_API_URL` and
`API_URL` stay unset for the web build).

**Later, Razorpay test mode** (once the adapter is finished, see
[deployment.md, appendix B](deployment.md#b-demo-payments-and-razorpay)):
`PAYMENT_MODE=razorpay`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`,
`RAZORPAY_WEBHOOK_SECRET` (test-mode keys, as Render secrets), and remove
`DEMO_MODE` and `PAYMENT_SECRET`.

### Development and test (your computer)

`backend/.env` and `backend/.env.test` from [.env.example](../.env.example),
with the Auth Emulator, `serve_dev` / `serve_test` and localhost origins
([development.md](development.md)). These values never go to Render.

## Database

- **Migrations** run automatically on every start (`prisma migrate deploy`).
  `prisma migrate reset`, `migrate dev` and `db push` are refused against any
  database not named `*_dev` / `*_test` and whenever `NODE_ENV=production`.
  Never delete the database to solve a migration problem.
- **Seed:** only the catalogue, and only when the database has no canteens.
  No test users, orders or payments are created.
- **Backups:** the free database has none. A paid Render Postgres plan has
  daily backups (and point-in-time recovery on higher plans).
- **Upgrading:** move to a paid instance in the database's settings, or
  create a paid database (or an external managed PostgreSQL 16), copy the data
  with `pg_dump` / `pg_restore`, and change `DATABASE_URL`. Allow an external
  connection temporarily for the copy (the database's **Access Control**),
  then remove it again.
- On a paid web service you can move the migrations to a **pre-deploy
  command** (`cd backend && ../node_modules/.bin/prisma migrate deploy`) and
  keep `start-production.sh` for the release tasks.

## Operations

- **Deploys:** every push to the connected branch redeploys (turn off auto-deploy in
  the service settings to deploy by hand). A failed build or start keeps the
  previous deploy live.
- **Rollback:** serve → **Events** → a previous deploy → **Rollback**. Database
  migrations are forward-only; see [deployment.md, step 19](deployment.md#19-rollback).
- **Logs:** serve → **Logs** (JSON lines; tokens and secrets are redacted).
- **Health:** Render probes `/api/health`; `/api/health/db` checks the database.

## Troubleshooting

| What you see | Cause and fix |
|---|---|
| Build fails in `build-web.mjs`: `set FIREBASE_API_KEY and FIREBASE_PROJECT_ID` | The two Firebase variables are missing on the service. Add them and redeploy. |
| Start fails with `Invalid environment configuration` | The log names the variable. Production refuses emulator settings, `demo-` projects, http/localhost origins and missing service-account values. |
| `/api/health/db` returns 503 | The database is unavailable (or has expired on the free plan). |
| `First admin not linked` | No Firebase user with `ADMIN_BOOTSTRAP_EMAIL`, or that account is already a student or staff member. |
| The first request is slow | A free service was asleep. |
| Students can't sign in from the mobile app | The API key has a website restriction; see step 6. |
